我现在的日常工作是高度多模型、多 Agent 的：好几个 agent 并行跑在不同项目上，背后接着一堆模型供应商。这种工作方式要对"稳定"和"低成本"同时不妥协，靠零敲碎打的配置是撑不住的——所以 DeepSeek 这次涨价之后，我不再多花心思在"怎么少花点"上，而是把问题反过来问：**我需要一套自己的基建，让任何一个供应商出问题（涨价、卡顿、改协议、抽风）都只是掉一条腿，而不是塌整个房子。**

<!-- more -->

## 这套基建要提供什么

想清楚之后，需求可以拆成四项，每一项都对应一类真实的事故来源：

**1. Agent 运行时。** 我的工作电脑会断电、会断网，一断，跑了一半的任务就没了。Agent 是我的主力劳动力这件事已经持续很久了，把劳动力拴在一台会跳闸的笔记本上是说不过去的。所以任务要能落到看板、由 runtime 领取、在容器里独立执行——机器断了，任务还在队列里等。这层我用 {% post_link Multica-AI原生的任务管理平台 [Multica] %}（对它思路的评价见 {% post_link 开源平替Claude_Managed_Agents的Multica到底是什么 [这篇] %}，日常使用里的吐槽在 {% post_link AI工具使用体验与吐槽-Multica-MiniMax-Google-One-Gemini [这篇] %}），runtime 本体是一个自建容器。

**2. 稳定、价格可接受的模型供应商。** 不能把鸡蛋放在一个篮子里——DeepSeek 涨价是一回事，更日常的是"今天这家突然卡了"。每家 token plan 商家都有自己的故障日和限流日，所以要多商家、多账户，谁家正常用谁家。这一层的选型和省钱逻辑（包括各家"最甜档位"的悖论）{% post_link Omniroute-DeepSeek涨价后-一个Key管起所有Token-Plan [上一篇] %}写得比较细，价格战的背景见 {% post_link DeepSeek-永久降价-大模型价格战的新玩法 [这篇] %}，我的用量量级在 {% post_link 三个月Token消耗暴涨13倍-我的AI工作流演变记录 [这里] %}。

**3. Agent 协议接入层。** 这是最被低估的一层。第三方 token 商家只管把推理卖给你，**不会管协议**：Codex 说 OpenAI 的 `responses`，Claude Code 说 Anthropic 的 `messages`，opencode 两边都要——方言不统一，就只能自己拿一层网关来翻译。

**4. MCP 网关（还没做，但在计划里）。** Agent 能用的工具越多越好，但工具本身也有管理成本：几十个 MCP server 的配置、鉴权、版本，散在各 agent 的 config 里迟早失控。我想再立一层把工具聚合起来统一管理。工具复用有 skill 和 MCP 两条路，我个人更倾向 MCP——它是协议层的复用，跨 agent 天然通用；skill 更像是某个 agent 的私有资产。

四项摆在一起，能看出一个趋势：我的 AI 基建不是"一个网关项目"，而是**运行时、供应商、协议、工具四层各自都要有归属**，每一层都得是我自己的，供应商只是最外面可替换的那层皮。

## 一处例外：科研工作台不走这条路

上面四项是我给自己定的规矩，但有一个工作台我故意没有按这套来办——**Claude Science**。

我拿它做 {% post_link Claude-Science-的好处与不完善之处 [科学研究] %}，并且 {% post_link 把Claude-Science装进Docker容器 [装进了 Docker 容器] %}——容器里垫一层 API Bridge，把后端换成 DeepSeek 官方 API 的 Anthropic 兼容模式，不需要持有 Anthropic 的 key。它和上面那套基建是**两个独立的东西**：不是 Multica 的一部分，也不共用它的运行时。

为什么它是例外？因为**科学研究比别的任务更需要即时交互**。写代码、跑批处理、整理数据，这些都可以"扔进看板，等结果回来"——Agent 干上二十分钟我完全可以不在场。但分析一张图、调一次参数、看一眼结果再决定下一步往哪走，这个循环里我必须在场，每多一次等待，思路就断一次。所以我到现在还在直接用 Claude Science，而不是把它改造成另一个 agent 任务。

也正因为这样，这个工作台是整套基建里**唯一不接任何第三方 token 商家的一角**。一家都没接——不是忘了，是不敢：我要的是它同时具备的三件事，官方 API 恰好都给到了。

- **多协议**：Claude Science 说 Anthropic 那套方言，官方 API 恰好有对应的兼容模式——容器里那层 Bridge 只做协议适配，不碰路由和额度。
- **图形（vision）**：读图是科研工作的日常，而且我还单独配了一个 vision fallback 环境变量，主模型不支持视觉时有东西能兜住。
- **联网**：查文献、抓资料都靠它，而第三方商家普遍不给你网络工具。

这个工作台反而成了"第一代方案"的活化石：多协议、vision、联网都是**在容器配置里用环境变量直配官方 API**——路由、额度、并发这些一概不管，图的就是少一层不确定。代价也很实在：它的配置和主链路完全不通用，同一个模型名我要在两处维护。

围绕它另有一整套周边坑，和主线无关，只列几个印象深的：为了让它能在容器里跑，我用 Go 写了个启动辅助程序，支持配置文件里写多个转发目标、启动时交互式选一个，命令本身可配置，还能不带容器单独跑；给它开显卡透传，结果把容器里的语言 kernel 全搞挂了，一路排查到 proc 挂载和设备映射才算完（{% post_link 容器内用opencode修复GPU直通 [这篇] %}）；容器里的 Python/R 绘图中文全变方框，得单独修字体。最离谱的是那个转发程序**被 Windows 当成病毒直接删除**——一个自己编译的 Go 小工具，没有签名，各家杀软各有各的想象力，最后只能研究上签名了。

## 每一项上踩过什么坑

### 运行时：每装一个新 agent，学费重交一遍

自建 runtime 容器的第一天就想清楚了：agent 不能以 root 跑，所以容器里单独建一个用户来执行；runtime 的状态目录和 agent 的配置目录全部映射到容器外持久化——否则每次重建容器，就得重新填一遍 model provider 信息；依赖环境一律交给 {% post_link 终于用pixi搞定了用于自动构建的recipe和action [pixi] %} 管，保证容器可复现。

之后的每一件事都是在交学费：

- **装一个 agent 就是一次独立的战役。** 今天装 Codex CLI 和 CodeBuddy，明天补 Claude Code 和一个能在这几家之间切 key、切 MCP、切 provider 的 CLI/TUI 工具（这类工具的存在本身就说明问题：客户端配置乱到有专人做管理器了）。
- **sandbox 类特性在容器里是多余的一层。** 带沙箱的 agent 默认假设自己面对一台完整的、还有别人在用的操作系统，进容器第一件事往往是先把 sandbox 特性关掉，否则连自己该读的文件都读不了。我后来想明白了这件事的性质：容器本身已经是隔离边界，再叠一层 sandbox 不是更安全，只是让 agent 处处碰壁。
- **容器里还要能起容器。** agent 需要跑 Docker 时，宿主机那层"容器内调用容器"是要专门开配置的，默认不给。
- **配置要能真正外化。** 一开始 key 和 URL 都是硬编码的，只能用一个供应商；后来才改成配置文件里可以写多个 key、并且能指定某个 agent 到底用哪一家的 key。这一步看似小，实际上是"多篮子"策略在客户端侧的地基。
- **规则要一次对所有 agent 生效。** 我给容器里的 agent 统一加了一条"写最少代码"的规则插件，配置落在镜像/初始化流程里，这样每次新容器长出来都自带。别小看这一步：agent 的行为规范如果靠每个仓库各自塞文件，迟早漂移。
- **协议透传的坑会在这层冒出来。** 用 dsh 配合 v4 pro 跑，普通对话一切正常，一进 thinking 模式就被上游打回：`The reasoning_content in the thinking mode must be passed back to the API`——thinking 模式下 reasoning 内容必须原样回传给 API，而这条请求链路没有回传。**同一个模型、同一个供应商，换个运行时就不行了**，这类问题网关帮不上忙，只能一层层看请求体。这条线后来还叠加了两件事：那个运行时自己升级后插件接口不兼容，以及它启动子进程时把环境洗了一遍、顺手抹掉了 runtime 需要的凭据，agent 连平台命令行都调不动。前后折腾了两个周末，最后的处理是**把它整个从运行时里删掉**——用一个还在不稳定期的运行时去省钱，这笔账算不过来。

这层真正的经验是：**runtime 不是一个程序，是一堆约定**。每接入一个新 agent，就要重新对齐一次"它的配置放哪、它能改什么、它假设自己有什么权限"。

### 供应商：老坑没修完，新坑接着来

omniroute 三个坑（搜索拦截不生效、新商家额度同步不了、默认禁止重型任务并发）{% post_link Omniroute-DeepSeek涨价后-一个Key管起所有Token-Plan [上一篇] %}已经写过，这里不重复。这层真正的教训是：**多篮子策略的维护成本比想象高**——篮子越多，"篮子之间"的胶水就越多，胶水本身又会成为新的单点。这个判断后来应验在了胶水自己身上：omniroute 这层中间件最后被我从运行时里整个拆掉了，上游统一收归 new-api，没配 token 的时候直接回退官方直连。省一层的诱惑很大，但维护两条链路永远比维护一条更贵。

### 协议接入层：一个周末没解决完的那一层

这层是我花时间最多、也是这篇文章里坑最多的，展开讲。

**第一代是直连官方 API。** 容器配置里直接接 DeepSeek 官方 API，Claude Code 走 Anthropic 模式，Codex 走 OpenAI 模式，另外给图形单独配一个 fallback 模型兜底。功能上没问题，但 base_url 散落在每个 agent 的 config 里，网关每上一个新模型，就得挨个客户端去补配置——这件事到今天还在重复：上游新上一个模型（比如 `deepseek-v4.1-flash`），除了在网关里登记，还得在每个客户端的模型清单里再声明一遍它支不支持图形输入。**"这个模型能看图"这种事实本该只有一处定义，实际却有五处。**中途我做过一次"全体切回官方 API、默认模型换成 vision 实验版"的大切换，那天我数了一遍要改几处地方——数完就决定不这么活了。

**第二代 omniroute 解决了"发到哪家"，没解决"用什么协议发"。** 它把供应商统一成一个入口、一个 key，这事很漂亮，但协议的债一分没还：它假设客户端和上游说同一种方言，而我的 agent 们不是。

**第三代死在 `responses` 上。** 换 new-api 是想让协议统一更彻底，结果上游 new-api 不支持 OpenAI 的 `responses` 协议——Codex 偏偏只会这一种。本地配好直连地址，请求直接不被支持。这不是配置能绕的，是两端协议栈对不上（这种"互不兼容"本身就是行业税，我在 {% post_link API-互不兼容-OpenAI和Anthropic的打印机耗材垄断策略 [《AI 时代的打印机耗材垄断》] %} 里吐槽过）。

更麻烦的是它**失败得很安静**。桥接的启用逻辑是启动时探测一下上游到底支持什么协议：能直连就不必多套一层转换。可 new-api 对 `POST /v1/responses` 的回应是 HTTP 400——按常识 400 是"你请求写错了"，于是探测逻辑把它归为"结论不明"，跳过桥接；而 Codex 依旧按 `responses` 直连，于是每次请求都失败。改成"只要不是 200 就启用桥接"之后才稳定下来。**协议层的坏消息经常长得像好消息**：没有异常栈、没有显式报错，只是该开的那层没开。

**第四代：再加一层 CLIProxyAPI 专门做协议转换。**

```
Codex → CLIProxyAPI(:8317) → new-api → 各家供应商
```

它的默认端口是 8317，Codex 这边要在 `~/.codex/config.toml` 里配一个自定义 provider，把 `base_url` 指过去，并把 `wire_api` 设成 `responses`（这是 Codex 侧的协议开关，也是这一层存在的全部理由）。[文档在这](https://help.router-for.me/introduction/quick-start.html)。至此我的完整链路长这样：

```
容器里的 agent（Codex / Claude Code / opencode / Reasonix / codebuddy）
   → CLIProxyAPI（协议转换）
   → new-api（路由与额度，未配 token 时回退官方直连）
   → 各家供应商
```

它能用了，代价是**每一层都有自己的配置和自己的默认值，故障定位变成了逐层砍链路的排除法**。我相当一部分排障时间不是在修问题，是在确认"到底哪一层坏了"。

而且这套胶水自己也会坏。有段时间 Codex 侧那个代理程序会周期性地返回 503：刚配好的时候一切正常，用上一阵子就开始报，重建容器又能安分几天。修完之后我记住的不是那个具体原因，而是"我刚亲手加的这一层，也需要有人看着"——**每多叠一层，就多一个会周期性失效的东西。**

**bifrost 和 apisix 停在评估，没上线。** 说明一下，这两个我都没真正部署过，所以这里只有"为什么没选"，没有编造的踩坑记录。bifrost 是 Go 写的高性能 LLM 网关，性能卖点很对我的胃口，但我需要的那件事——同一个入口同时喂 OpenAI 和 Anthropic 两套方言的客户端——恰是各网关能力参差最大的地方，README 看不出来，必须上真实流量验；评估它的时候 omniroute 已经扛着日常了，这件事就一直没腾出手。apisix 是另一个物种：通用 API 网关 + AI 插件，意味着自己养一套 etcd 加 APISIX，路由和插件配置全手写。我的场景是一个人加几个 agent，为一台机器上的几个客户端部署生产级流量网关，是拿大炮打蚊子。

### MCP 网关：还没建，所以也没坑

不编不存在的东西。这层排期靠后是有原因的：**上一级的协议层还没稳定，工具层动了也是白动**。等网关这层沉淀下来，再看是自建聚合还是接现成的 MCP gateway。

不过工具层其实已经有一半在动了，只是它不叫 MCP：浏览器。让 agent 能上网——共享已登录的浏览器状态、点页面、抓内容——这件事我评估过一圈，停在"方案评估"上没有落地：上游那个给 agent 用的浏览器只发 macOS 安装包，Linux 侧是社区移植，要往容器里额外塞一套 Chrome 加 CDP 桥。它和 MCP 网关是同一个问题的两面：**工具的价值取决于 agent 能不能稳定地用上它，而稳定的前提是有人替它把环境维护好。**

## 做基建不容易，但它是唯一能把工作推下去的办法

协议接入层那一段，我搭了一个周末，没解决。第二个周末搭进去一半，链路勉强通了，然后开始排"到底哪一层坏了"——到现在也没到一个我满意的终点。这种投入在日常工作里是很奢侈的：它不产出任何业务代码，纯粹是在给未来的工作铺路。

但换个角度算账就不奢侈了。多 Agent 并行的收益我在 {% post_link 对Agent收益的思考 [这篇] %} 里认真算过：agent 的收益取决于它能不间断地干活。供应商卡一次、商家改一次价、协议不兼容一次，停下来的是整条流水线——而**基建的价值恰恰体现在它不需要被注意的那些日子**：什么都没发生，任务跑完了，你甚至不记得自己上周还修过网关。

现在这套东西仍然谈不上优雅：四层链路、配置没有单一事实来源、成本观测是空的、链路没有健康检查。中间还拆回去过两条——一个中间件、一个不稳定期的运行时——拆的过程比装更费时间。但至少"明天换一家供应商"这件事，从"重写所有客户端配置"变成了"改一行配置，再补一份协议转换"。

一个周末没搭完的基建，下个周末继续搭就是了。
