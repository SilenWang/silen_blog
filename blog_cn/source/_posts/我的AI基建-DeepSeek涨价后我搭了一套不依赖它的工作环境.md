这篇记录的是我这半年折腾自己那套 AI 工作环境的完整过程：为什么非要不依赖 DeepSeek 的 API、翻过哪些方案、每一层各留下什么坑。它是我之前那篇 {% post_link Omniroute-DeepSeek涨价后-一个Key管起所有Token-Plan [《Omniroute：一个 Key 管起所有 Token Plan》] %} 的下文——那篇写的是"选了 omniroute"，这篇写的是"选完之后发现还得再叠好几层"。

<!-- more -->

## 涨价只是导火索

DeepSeek 正式涨价，我第一反应是无所谓：它本来就很便宜，涨完还是比 V4 刚公布定价时低。但实测一天之后我算错了——我的量实在太大（{% post_link 三个月Token消耗暴涨13倍-我的AI工作流演变记录 [上季度 Token 消耗奔着上亿去] %}），贵一点都是割肉，再不想办法就是付费上班。

但省钱的路子探到一半，我意识到真正的问题不是钱。

我全部的工作环境——容器、几个 agent、模型配置、启动脚本——都拴在**一个云端 API 端点**上。涨价能忍，那哪天它改协议、改限流、改模型名、或者直接抽风几小时呢？我这两年遇到的"我的 agent 突然不能用了"，多半都是这一层的问题，而我对它没有任何控制权。

所以我给自己定的目标变成了：**搭一套不依赖 DeepSeek API 的工作环境**。

先把话说清楚，避免误解：我说的不是自己跑模型。我也认真想过本地部署，但手头这台机器跑不动能干活的大模型，量一算就放弃了。我要拿回来的只是**入口层**的控制权——端点、路由、计费、协议转换这几件事必须在我自己机器上，上面接谁家的模型可以随便换。API 我可以继续买，但不能是"只能用它"。

## 这套东西长什么样

摸清全貌之后再回头看，我的基建其实就三层：

```
容器（我的工作区，agent 在里面跑）
  └─ 启动器（Go 写的小程序，决定这一轮把请求转到哪）
      └─ 网关层（omniroute / new-api / CLIProxyAPI / 官方直连，可组合）
```

最上面那层是最近半年才慢慢长出来的，底下两层其实早就有了。最早我甚至手写过一个小中转程序（`codex-deepseek-bridge`），专门用来在 Codex 和 DeepSeek 之间倒协议——那时候我就该明白，协议这层迟早要还。

## 第一代：直连官方 API

一开始的方案简单粗暴，就是在容器配置里直接接 DeepSeek 官方 API。它有两个接口，各家的 agent 吃哪个就用哪个：Claude Code 这类走 **Anthropic 模式**，Codex 这类走 **OpenAI 模式**（我一开始想给 Codex 接 DeepSeek，就是被这个协议不兼容卡住的，最后只能按官方那套方式接）。

配置层还顺手解决了一个问题：**图形（vision）的 fallback 模型**。主模型不支持视觉时，得有个兜底的模型顶上，所以 vision 单独留了一份可配置的环境变量。

第一代的问题不在功能，全在配置上：

- **base_url 散落各处**。Codex 一份、Claude Code 一份、opencode 一份，Reasonix 再加一份，每多一个 agent 就多一处要改。
- **每加一个模型，配置就要在所有地方写一遍**。后来 omniroute 那边上新了一个免费模型，我得逐个回答"你的 config 里加了没有"。
- 中途我做过一次大动作：把所有请求整体切回官方 API，默认模型换成一个 vision 实验版（界面上仍显示成稳定的那个名字，vision fallback 也换成同一个）。切换那天我数了下要改几处地方——就是从这里开始，我确信不能再这么过了。

第一代唯一的优点，是那个 Go 启动器。它支持配置多个转发目标、启动时交互式选一个、命令本身可配置，还能不带容器单独跑。它已经隐约是个路由器了，只是它只会"整条换"，不会"按请求分"。

## 第二代：omniroute，一个 Key 管所有

于是上了 omniroute——把各家 token plan 聚合成一个入口，客户端只需要一个 Key，想换商家在控制台点一下，客户端完全无感。详细过程那篇 {% post_link Omniroute-DeepSeek涨价后-一个Key管起所有Token-Plan [《Omniroute》] %} 写过了，这里只留三个坑的名字和一个新坑。

1. 搜索拦截匹配不上带版本号的工具名，Codex 和 Claude Code 搜不了网；
2. 太新的商家同步不了额度，"额度感知的自动回退"直接失效；
3. 默认不允许重型任务并发，多子 agent 一并行就突然断流。

新坑是这半年才显出来的：**模型元数据要一份份手抄**。网关侧上新一个模型，并不意味着各客户端就能用——Codex 的 `config.toml`、opencode 的配置、Reasonix 的配置，得一个一个跟着改。网关统一了 Key，但没有统一"模型清单"这件事。

更根本的是：omniroute 管住了"发到哪家"，一点没管"用什么协议发"。而我的 agent 用的协议根本不是一套。

## 第三代：new-api，结果被协议卡死

换到 new-api，是觉得它做"多协议统一"更彻底，正好治上面那个病。

结果死在一个很具体的点上：**上游 new-api 不支持 OpenAI 的 `responses` 协议**。而 Codex 偏偏就说这一种方言，本地配好直连地址后，请求直接就不支持。这不是配置能绕的，是两端协议栈对不上。

## 第四代：再叠一层 CLIProxyAPI 做协议转换

绕过的办法是**再加一层**。装上 CLIProxyAPI，专门把 Codex 的 `responses` 协议转换后再转给 new-api。

```
Codex → CLIProxyAPI(:8317) → new-api → 各家模型供应商
```

它的默认端口是 8317，Codex 这边要在 `~/.codex/config.toml` 里配一个自定义 provider，写清 `base_url` 指过去，并把 `wire_api` 设成 `responses`（这是 Codex 侧的协议开关，也是整层存在的理由）。

到这里我的链路长这样：

```
容器里的 agent（Codex / Claude Code / opencode / Reasonix / dsh / codebuddy）
   → CLIProxyAPI（协议转换）
   → omniroute 或 new-api（路由与额度）
   → 各家供应商
```

它确实能用了。然后所有故障都变得极难排查：agent 行为不对，可能是容器里那份 config、可能是 CLIProxyAPI、可能是网关、可能是上游商家。四层，每一层都有自己的配置和自己的默认值。我花了大概一半的排障时间用来确认"到底哪一层坏了"——而确认的方法是把链路逐层砍短。

## bifrost 和 apisix：停在评估，没上线

这两家我都在候选名单上看过，但都没真正部署过，所以这里写的是"我为什么没选"，不是踩坑记录。

**bifrost** 想用 Go 做一个高性能的大模型网关，性能卖点确实对味。但要的东西它给不了：我这一层需要的是"能同时把 OpenAI 和 Anthropic 两套方言喂给我的 agent"，而这恰好是各网关能力参差最大的地方，光看 README 判断不了，只能上机验——而我评估它的时候手上 omniroute 已经跑着，没腾出手，这件事就搁下了。

**apisix** 是完全另一种东西。它本身是通用 API 网关，AI 能力是靠插件挂上去的，代价是要先养一套 etcd 加 APISIX，还得自己写路由和插件配置。我真正想解决的只是一个"我 + 几个 agent"的问题——为一台机器上的五个客户端部署一套为生产流量设计的网关，是拿大炮打蚊子。

## 现在还没解决的问题

- **没有标准**。`responses` / `chat completions` / `messages` 三套方言，网关只能不停翻译。这件事不是某个项目的 bug，是行业在交互不兼容的税（我在 {% post_link API-互不兼容-OpenAI和Anthropic的打印机耗材垄断策略 [《AI 时代的打印机耗材垄断》] %} 里吐槽过）。
- **配置仍然散**。网关只统一了端点，模型清单还是得一份份抄。真想根治，得有一份单一事实来源的配置去生成各客户端的 config——这一步我还没做。
- **成本观测是空的**。网关只负责路由，不告诉我钱花在哪。
- **链路没有健康检查**。四层里挂一层，表现都是"agent 不干活了"。

## 小结

回头看，"不依赖某个 API"这件事，最后我并没有做到——我依赖的供应商反而比一开始多了。但目标本身其实达成了：入口这一层现在在我手里，换供应商是改一行配置，而不是重写五处客户端设置。

代价是多了三四个组件和一段谁都不想看第二次的排障链路。这买卖划不划算，我现在也说不好，可能明年这篇文章会有一篇续集专门讲我把它拆掉了。
