我现在的日常工作是高度多模型、多 Agent 的：好几个 agent 并行跑在不同项目上，背后接着一堆模型供应商。这种工作方式要对"稳定"和"低成本"同时不妥协，靠零敲碎打的配置是撑不住的——所以 DeepSeek 这次涨价之后，我不再多花心思在"怎么少花点"上，而是把问题反过来问：**我需要一套自己的基建，让任何一个供应商出问题（涨价、卡顿、改协议、抽风）都只是掉一条腿，而不是塌整个房子。**

<!-- more -->

## 这套基建要提供什么

想清楚之后，需求可以拆成四项，每一项都对应一类真实的事故来源：

**1. Agent 运行时。** 我的工作电脑会断电、会断网，一断，跑了一半的任务就没了。Agent 是主力劳动力这件事已经持续大半年了，劳动力拴在一台会跳闸的笔记本上是说不过去的。所以任务要能落到看板、由 runtime 领取、在容器里独立执行，机器断了任务还在队列里等着——这层我用的是 {% post_link Multica-AI原生的任务管理平台 [Multica] %}（对这套思路的评价见 {% post_link 开源平替Claude_Managed_Agents的Multica到底是什么 [这篇] %}），容器环境的搭建过程在 {% post_link 把Claude-Science装进Docker容器 [这里] %} 写过。

**2. 稳定、价格可接受的模型供应商。** 不能把鸡蛋放在一个篮子里——DeepSeek 涨价是一回事，更日常的是"今天这家突然卡了"。每家 token plan 商家都有自己的故障日和限流日，所以要多商家、多账户，谁家正常用谁家。这一层的选型和省钱逻辑（包括各家"最甜档位"的悖论）{% post_link Omniroute-DeepSeek涨价后-一个Key管起所有Token-Plan [上一篇] %}写得比较细，价格战的背景见 {% post_link DeepSeek-永久降价-大模型价格战的新玩法 [这篇] %}，我的用量量级在 {% post_link 三个月Token消耗暴涨13倍-我的AI工作流演变记录 [这里] %}。

**3. Agent 协议接入层。** 这是最被低估的一层。第三方 token 商家只管把推理卖给你，**不会管协议**：Codex 说 OpenAI 的 `responses`，Claude Code 说 Anthropic 的 `messages`，opencode 两边都要——方言不统一，就只能自己拿一层网关来翻译。

**4. MCP 网关（还没做，但在计划里）。** Agent 能用的工具越多越好，但工具本身也有管理成本：几十个 MCP server 的配置、鉴权、版本，散在各 agent 的 config 里迟早失控。我想再立一层把工具聚合起来统一管理。工具复用有 skill 和 MCP 两条路，我个人更倾向 MCP——它是协议层的复用，跨 agent 天然通用；skill 更像是某个 agent 的私有资产。

四项摆在一起，能看出一个趋势：我的 AI 基建不是"一个网关项目"，而是**运行时、供应商、协议、工具四层各自都要有归属**，每一层都得是我自己的，供应商只是最外面可替换的那层皮。

## 每一项上踩过什么坑

### 运行时：环境是踩坑的大头

这层的坑基本都不是 Multica 的，而是"容器里装什么、怎么装"。agent 在容器里跑，环境就必须可复现，我用 {% post_link 终于用pixi搞定了用于自动构建的recipe和action [pixi] %} 管依赖，构建 recipe 那篇把过程写全了。另一个反复出现的坑是权限模型：Reasonix 这类带 sandbox 的 agent 默认假设自己有完整操作系统，在容器里得先关掉 sandbox 类特性才能跑——每一个新 agent 进容器，都要重新交一遍这种学费。

### 供应商：老坑没修完，新坑接着来

omniroute 三个坑（搜索拦截不生效、新商家额度同步不了、默认禁止重型任务并发）{% post_link Omniroute-DeepSeek涨价后-一个Key管起所有Token-Plan [上一篇] %}已经写过，这里不重复。这层真正的教训是：**多篮子策略的维护成本比想象高**——篮子越多，"篮子之间"的胶水就越多，胶水本身又会成为新的单点。

### 协议接入层：一个周末没解决完的那一层

这层是我花时间最多、也是这篇文章里坑最多的，展开讲。

**第一代是直连官方 API。** 容器配置里直接接 DeepSeek 官方 API，Claude Code 走 Anthropic 模式，Codex 走 OpenAI 模式，另外给图形（vision）单独配一个 fallback 模型兜底。功能上没问题，但 base_url 散落在每个 agent 的 config 里，网关每上一个新模型，就得挨个客户端去补配置。中途我做过一次"全体切回官方 API、默认模型换成 vision 实验版"的大切换，那天我数了一遍要改几处地方——数完就决定不这么活了。

**第二代 omniroute 解决了"发到哪家"，没解决"用什么协议发"。** 它把供应商统一成一个入口、一个 key，这事很漂亮，但协议的债一分没还：它假设客户端和上游说同一种方言，而我的 agent 们不是。

**第三代死在 `responses` 上。** 换 new-api 是想让协议统一更彻底，结果上游 new-api 不支持 OpenAI 的 `responses` 协议——Codex 偏偏只会这一种。本地配好直连地址，请求直接不被支持。这不是配置能绕的，是两端协议栈对不上（这种"互不兼容"本身就是行业税，我在 {% post_link API-互不兼容-OpenAI和Anthropic的打印机耗材垄断策略 [《AI 时代的打印机耗材垄断》] %} 里吐槽过）。

**第四代：再加一层 CLIProxyAPI 专门做协议转换。**

```
Codex → CLIProxyAPI(:8317) → new-api → 各家供应商
```

它的默认端口是 8317，Codex 这边要在 `~/.codex/config.toml` 里配一个自定义 provider，把 `base_url` 指过去，并把 `wire_api` 设成 `responses`（这是 Codex 侧的协议开关，也是这一层存在的全部理由）。[文档在这](https://help.router-for.me/introduction/quick-start.html)。至此我的完整链路长这样：

```
容器里的 agent（Codex / Claude Code / opencode / Reasonix / dsh / codebuddy）
   → CLIProxyAPI（协议转换）
   → omniroute 或 new-api（路由与额度）
   → 各家供应商
```

它能用了，代价是**每一层都有自己的配置和自己的默认值，故障定位变成了逐层砍链路的排除法**。我相当一部分排障时间不是在修问题，是在确认"到底哪一层坏了"。

**bifrost 和 apisix 停在评估，没上线。** 说明一下，这两个我都没真正部署过，所以这里只有"为什么没选"，没有编造的踩坑记录。bifrost 是 Go 写的高性能 LLM 网关，性能卖点很对我的胃口，但我需要的那件事——同一个入口同时喂 OpenAI 和 Anthropic 两套方言的客户端——恰是各网关能力参差最大的地方，README 看不出来，必须上真实流量验；评估它的时候 omniroute 已经扛着日常了，这件事就一直没腾出手。apisix 是另一个物种：通用 API 网关 + AI 插件，意味着自己养一套 etcd 加 APISIX，路由和插件配置全手写。我的场景是一个人加几个 agent，为一台机器上的几个客户端部署生产级流量网关，是拿大炮打蚊子。

### MCP 网关：还没建，所以也没坑

不编不存在的东西。这层排期靠后是有原因的：**上一级的协议层还没稳定，工具层动了也是白动**。等网关这层沉淀下来，再看是自建聚合还是接现成的 MCP gateway。

## 做基建不容易，但它是唯一能把工作推下去的办法

协议接入层那一段，我搭了一个周末，没解决。第二个周末搭进去一半，链路勉强通了，然后开始排"到底哪一层坏了"——到现在也没到一个我满意的终点。这种投入在日常工作里是很奢侈的：它不产出任何业务代码，纯粹是在给未来的工作铺路。

但换个角度算账就不奢侈了。多 Agent 并行的收益我在 {% post_link 对Agent收益的思考 [这篇] %} 里认真算过：agent 的收益取决于它能不间断地干活。供应商卡一次、商家改一次价、协议不兼容一次，停下来的是整条流水线——而**基建的价值恰恰体现在它不需要被注意的那些日子**：什么都没发生，任务跑完了，你甚至不记得自己上周还修过网关。

现在这套东西仍然谈不上优雅：四层链路、配置没有单一事实来源、成本观测是空的、链路没有健康检查。但至少"明天换一家供应商"这件事，从"重写所有客户端配置"变成了"改一行配置，再补一份协议转换"。

一个周末没搭完的基建，下个周末继续搭就是了。
